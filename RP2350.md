# FlashFloppy on RP2350 (Raspberry Pi Pico 2)

This port runs the standard FlashFloppy *shugart* firmware on a
Raspberry Pi Pico 2 (RP2350). Disk images live on an **SD card** (SPI
mode) instead of a USB stick, or, with no card fitted, in a **FAT**
image held in the Pico's own QSPI flash. It remains bare-metal: no
pico-sdk, no TinyUSB (the USB serial console is a few hundred lines of
register poking).

## How it works

- `clk_sys` runs at **144MHz** so the PIO flux engine, at two PIO cycles
  per tick, reproduces the exact 72MHz SAMPLECLK used by the STM32
  firmware. All image decoding and bitcell arithmetic is unchanged.
- **RDATA** is generated by PIO0 SM0: DMA streams 16-bit flux intervals
  from the same ring buffer the STM32 code uses into the TX FIFO; the SM
  emits a fixed 388ns active-low pulse per interval.
- **WDATA** is captured by PIO0 SM1: a free-running 16-bit counter is
  sampled at each falling edge and pushed through DMA into the write
  ring, mimicking the STM32 timer input-capture semantics.
- Bus outputs are **driven push-pull at 3.3V while selected**, as the
  Gotek drives them: asserted lines low, everything else actively high, so
  no line is left to the host's pull-up and cable noise between assertions.
  Deselect tri-states the whole bus with a single SIO `GPIO_OE` write. Pins
  whose bus line is unmapped in the current interface mode stay inputs (bus
  pin 2 is the controller-driven DENSEL on a PC cable).
- The firmware is copied to **SRAM at boot** and runs entirely from RAM:
  flash (XIP) timing can never disturb flux generation. QSPI flash is
  touched only for the internal image store (above 1MB) and to store
  `FF.CFG` settings (final 4kB sector below the 1MB boundary), via
  bootrom flash routines.
- `verify PIO timing`: `python3 scripts/check_pio_timing.py`.

## Image storage

At startup the firmware looks for an SD card first. If none mounts, it
falls back to a FAT16 volume occupying flash from **1MB to 4MB** --
above the firmware and its `FF.CFG` sector, and clear of them. It is an
ordinary FAT volume behind an ordinary block device (`flash_vol.c`), so
everything works exactly as it does on a card: directory navigation,
`FF.CFG`/`IMG.CFG`, HxC selector mode, Direct Access, and **writes** --
host writes to the emulated floppy, `IMAGE_A.CFG` (the last-selected
image is remembered across power cycles), and the eject menu's
Copy/Paste/Delete all land in the internal flash.

A sector write is a read-modify-write of the 4kB flash erase block
containing it, performed with interrupts disabled (a few tens of
milliseconds for the erase). Rewrites of identical data are skipped, so
FAT and directory sectors that FatFS syncs repeatedly do not wear the
flash. Still, QSPI flash endures ~100k erase cycles per block: fine for
saves and config updates, not for a host that writes continuously.

### Building and flashing an image store

`scripts/mk_fat.py` turns a directory into a FAT image. It needs only a
stock Python 3:

```
python3 scripts/mk_fat.py my_disks/ fs.uf2
```

This writes `fs.bin` (the raw volume, truncated after the last used
cluster) and `fs.uf2` (the same bytes, addressed at 0x10100000). Install
it either by dropping `fs.uf2` on the RP2350 BOOTSEL drive, or with:

```
picotool load -o 0x10100000 fs.bin
```

Flashing the firmware and flashing the image store are independent: a
`target.uf2` update leaves your disk images alone, and vice versa.

The volume always claims the full 3MB; the output files cover only the
sectors actually allocated, so the UF2 is roughly the size of your
images. Any tool that produces a 512-byte-per-sector FAT16 superfloppy
(no partition table) up to 3MB works too -- e.g. mtools' `mformat` --
`mk_fat.py` is just a dependency-free way to get one.

To pull back images the host has written, dump the store and mount it
loopback (it is a plain FAT image):

```
picotool save -r 0x10100000 0x10400000 fs.bin
```

### Limitations

- **An SD card inserted after boot is not picked up.** The card is
  probed once, at mount time; reset the board to switch to it.

GPIOs 2-14 carry the thirteen bus signal lines **in bus-pin order**, so a
34-way header can be wired straight across without crossovers. For bus
pins 16 to 34 the relation is simply `bus = GPIO*2 + 6`.

## Wiring notes

- RP2350 GPIOs are **5V-tolerant while IOVDD is powered** (the datasheet's
  condition: IOVDD must be up whenever 5V is applied to a pad, otherwise
  the pad is damaged), so the floppy-bus inputs connect directly. The
  caveat is power *sequencing*, not steady state: a Pico that is unpowered
  while plugged into a live host has the host's bus pull-ups presenting 5V
  to unpowered pads. Power the Pico from the host machine's own supply, or
  before it; fit ~1k series resistors in the bus lines if that cannot be
  guaranteed.
- Outputs are driven push-pull at 3.3V while the drive is selected, and
  tri-stated when it is not. 3.3V is comfortably above the 2.0V TTL input
  threshold, and a driving pad never sees 5V (it holds the line itself);
  deselected pins are inputs, which is the state the 5V tolerance covers.
  Asserting still means sinking the host's termination current, so the
  outputs use the pad's strongest (12mA) drive: ample against the 1k
  pull-up a PC motherboard uses, not enough against a 150-ohm terminator
  pack. A bare drive-less bench setup needs no pull-ups on the outputs.
- The bus *inputs* enable the pad's own weak (~50k) pull-up, so an
  unconnected or undriven line reads as deasserted rather than floating and
  oscillating. That is enough for a line the host actually drives, but it is
  no substitute for the host's termination: a long unterminated ribbon can
  still ring badly enough to produce spurious STEP edges, which is what the
  glitch filter described below exists to absorb. MOTOR is the exception and is pulled *down*, so that an
  unconnected MOTOR reads as asserted (motor always on).
- SD card: any 3.3V SPI micro-SD breakout. Runs at 400kHz during init,
  then 24MHz.
- Display: standard FlashFloppy I2C SSD1306/SH1106 OLED or HD44780+
  PCF8574 LCD on GPIO 20/21 (3.3V; external 2.2k-4.7k pull-ups
  recommended). A TM1651 3-digit LED display is also supported on the
  same two pins.
- JC (GPIO28): leave open for Shugart, strap to GND for IBM PC mode
  (same as the Gotek JC jumper).
- On-board LED (GPIO25): lit whenever the host has this drive selected,
  like the front-panel LED of a real floppy drive. (Pico 2 W wires its LED
  to the wireless module rather than GPIO25, so it stays dark there.)
- The board's own micro-USB socket is a serial console and a route into
  BOOTSEL; see below. It needs no GPIOs -- USB has dedicated pins.

## Building

```
make target mcu=rp2350 target=shugart level=prod   # one target
make prod-rp2350                                   # same thing
make debug-rp2350                                  # serial console build
```

The debug build's console goes to both USB CDC and UART0; see "USB serial
console" below.

Output: `out/rp2350/<level>/shugart/target.uf2`.

## USB serial console

The Pico 2's own USB socket presents a **USB CDC-ACM serial port**
(`2E8A:000A`, the same IDs the pico-sdk uses), implemented bare-metal in
`src/pico2/usb_cdc.c` -- no TinyUSB. It appears as `/dev/ttyACM0` on
Linux, `/dev/cu.usbmodem*` on macOS, and a COM port on Windows.

Debug builds write the console to this port *and* to UART0 on GPIO 0/1,
so either can be used. The line rate is ignored: CDC has no real baud
rate. Console input is discarded.

The port exists in `prod` builds too, silent apart from the reset gesture
below.

### 1200-baud reset to BOOTSEL

As on Arduino boards, **opening the serial port at 1200 baud and closing
it again reboots the board into BOOTSEL**, ready to accept a UF2. No
BOOTSEL button press and no unplugging:

```
# Linux
stty -F /dev/ttyACM0 1200 && sleep 1 && cp target.uf2 /media/$USER/RP2350/
# macOS
stty -f /dev/cu.usbmodem1101 1200
```

The trigger is the same one Arduino uses: a line rate of exactly 1200
baud, plus DTR deasserted (which is what closing the port does). Both
orderings work -- set 1200 then close, or close a port that was already
at 1200. The reboot goes through the bootrom's `reboot()` call and takes
effect about 10ms later, after the control transfer has been
acknowledged, so the host sees a clean disconnect.

Note that this works whenever the port is at 1200 baud, including in the
middle of disk emulation. Terminal programs configured for 1200 baud
will therefore drop the board into BOOTSEL when they exit.

## Flashing

Hold BOOTSEL while plugging the Pico 2 into USB, then copy `target.uf2`
to the `RP2350` drive. There is no FlashFloppy bootloader on this
platform: firmware update is always via BOOTSEL, or via the 1200-baud
gesture described above.

See "Image storage" above for putting disk images into the internal
flash.

## Limitations (v1 of the port)

- *shugart* target only: `apple2`, `quickdisk`, `io_test`, and the
  legacy bootloader/`bl_update` targets are not built for RP2350.
- USB stick storage is not supported (SD card, or internal flash). The
  USB controller runs in *device* mode, as a serial console.
- FF OSD (I2C display OSD device) is not supported.
- The `CHGRST_pa14` (dedicated change-reset input) config option is not
  supported; use `chgrst=step` or a delay.
- Index-pulse alignment to the flux stream is accurate to roughly one
  flux sample (a few microseconds per revolution) rather than the STM32's
  sub-sample precision. This is well inside host tolerances.
